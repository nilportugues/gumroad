# Workstreams

Each workstream is sized for one worktree and one owner (person or agent). Read
[README.md](README.md) first: the parity rules there apply to every stream.

**Scope: everything ports.** Every route, page and job moves to Node. A "hands back to Rails" path (payments, mail, signed
tokens, Stripe/PayPal, S3, throttled routes) is parity debt to be paid down, not a permanent boundary; the way to remove it is
the same as for any other port: recorded Rails fixtures, with VCR or WebMock recordings standing in for the external service.

## Picking one up

```bash
git fetch origin
git worktree add ../gumroad-ws-12 -b nextjs/ws-12-products origin/nextjs-rewrite
cd ../gumroad-ws-12/nextjs && npm install && cp .env.example .env
```

Then:

1. Check the stream's **Depends on**. Do not start until those are merged into `nextjs-rewrite`.
2. Port Ruby file by file, keeping a mapping comment at the top of each TypeScript file
   (`// Port of app/services/foo/bar.rb`). Reviewers diff the two side by side.
3. Prove parity with the WS-01 tools. A port without a parity check is not done.
4. Open the PR against `nextjs-rewrite`, not `main`, and tick the stream in the README status list.
5. Keep PRs near 100 lines of logic where possible (CONTRIBUTING.md); a stream is many PRs.

**Shared contracts:** `nextjs/src/server/auth/context.ts`, `server/jobs/enqueue.ts` and
`server/infra/config.ts` are committed as typed stubs. Their owners (WS-03, WS-05, WS-06) implement them
without changing the signatures; everyone else imports them as if they already work.

**Collision rule:** a stream owns the directories listed under **Owns**. Anything outside them that
needs to change (a shared model service, the navigation compat module) goes in its own small PR to
`nextjs-rewrite` first, so two streams never edit the same file in parallel.

## Phase 3 and 4

### WS-30 Jobs and cron

Port the 303 job bodies into the Node worker designed in WS-05, queue by queue starting with `low`.
A job moves when its enqueuers are already in Node or still enqueue the same wire format (they do, by
design). `critical` (receipts) moves last.

**Standing fallback stream.** WS-30 runs continuously, not only in phase 3. Whenever a route workstream would conflict with
one already running (same controller, same `routes.json` block, same lane) or is blocked (money, mail, signed tokens, an
unported presenter), a free worktree picks up the next Sidekiq job here instead of idling.

- **Order:** `low` first, then `default`; `critical` stays last. Take a job whose enqueuers already live in Node or enqueue the
  same wire format. `remaining-work.md` lists the classes still `runtime: ruby`; many Node jobs hand individual runs back to
  Ruby, so look at the hand-backs before counting a job as done.
- **Parity proof:** record the job's inputs and effects from Rails (DB row diff, jobs pushed, mails, external calls) with
  `parity: true`, replay them against the Node job, and keep a "hands a ..." example for each run it gives back. A job that
  sends mail, calls Stripe/PayPal, writes to S3 or moves money keeps handing that part back before any write.
- **Conflicts:** jobs live in `src/worker/jobs` and the generated `registry.generated.ts`, so they rarely touch the files route
  ports edit; regenerate the registry and `remaining-work.md` rather than merging them by hand.
